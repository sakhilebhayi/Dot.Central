# Dot.Central

Purpose: this is Dot.Central's own knowledge home — owned and maintained by the Dot.Central team. It describes what this platform actually is, how it's built, and how it connects to the wider Dot Ecosystem. Dot.Brain never edits this file; it only reads what we choose to publish.

> **Related:** [Dot.Brain's ingested view of this platform](https://github.com/sakhilebhayi/Dot.Brain/blob/main/platforms/dot-central.md)

---

## 1. What Dot.Central Is

Dot.Central now hosts two domains side by side in the same codebase:

1. **AI command centre** — the place teams build, configure, and converse with specialised Claude-powered agents, then route work from other Dot platforms through them.
2. **Mining-dispatch scaffold (MVP, added 2026-08-01)** — the operational-intelligence data model described in Dot.Brain's `platforms/dot-central.md`: control rooms, dispatch decisions, alerts, and operator sessions. This is a data-model-and-CRUD scaffold only; see §3a and §7 for exactly what is and isn't built.

It is a Laravel 12 application (Livewire 3, Alpine.js, Tailwind, PostgreSQL) with Jetstream-based teams/auth and Sanctum-backed ecosystem SSO.

**Status:** early build on both domains. AI command-centre core loop — create an agent, start a conversation, chat with it — is genuinely reachable and working as of 2026-08-10 (§7). That corrects this section's own prior claim: earlier versions of this wiki said the AI command-centre was "implemented and running," but that only meant the database schema and `AgentChatService`'s Claude integration existed — there was no route to create an agent, no route to open a conversation, and `AgentChat`'s own Blade view didn't exist at all (would have thrown `ViewNotFoundException` the instant it rendered). Nothing had ever exercised that path, which is why it went unnoticed. Deeper AI-domain features (knowledge-base grounding per agent, multi-agent routing/chaining, streaming responses, per-agent public API endpoints) are named in the README as intended direction but not yet built out in code. The mining-dispatch domain has migrations, models, basic CRUD (controllers + Blade views), factories, and a seeder standing, scoped to Jetstream teams the same way the rest of the app is, plus (2026-08-09) this platform's first background automation — a scheduled command that raises alerts and opens human-reviewed proposals on operator-session inactivity, see §3a — but still no event emission out to an ecosystem event bus, no Dot.Mines integration, and no Knowledge Pack publishing.

## 2. Architecture

| Layer | Technology |
|---|---|
| Framework | Laravel 12, PHP 8.4 |
| Frontend | Livewire 3, Alpine.js 3, Tailwind CSS |
| Database | PostgreSQL 16 (shared ecosystem instance) |
| Auth | Laravel Jetstream (teams) + Sanctum, with `EcosystemAuthController` handling SSO handoff from the InfoDot hub |
| AI | Anthropic Claude via direct HTTP call to `https://api.anthropic.com/v1/messages` (default model `claude-sonnet-4-6`), wrapped in `App\Services\AgentChatService` |
| Realtime (planned) | Laravel Reverb |
| Search (planned) | Laravel Scout / Meilisearch |
| Queue (planned) | Redis / Laravel Horizon |

"Realtime (planned)" was checked directly, not assumed, during the 2026-08-10 streaming design work (below): `laravel/reverb` is a `composer.json` dependency, but `config/broadcasting.php` doesn't exist, there's no JS Echo client anywhere in `resources/js`, and no code anywhere references `Broadcast`/`ShouldBroadcast`/`Echo`. "Planned" is the accurate word — it's an installed-but-entirely-unused dependency, not real infrastructure something could be quietly relying on.

`AgentChatService::chat()` persists the user message, calls the Anthropic Messages API with the agent's `system_prompt` and full conversation history, persists the assistant reply, and logs token usage — as of 2026-08-10, this happens via a genuinely streamed request (`"stream": true`, Anthropic's own Server-Sent Events parsed as bytes arrive and pushed to the browser via Livewire's native `stream()`), not one blocking call; see §7. When `ANTHROPIC_API_KEY` is unset it falls back to a mock echo reply so the app runs without a live key — a deliberate dev-mode fallback, not a bug.

## 3. Domain Entities

| Entity | Table | Key fields | Notes |
|---|---|---|---|
| Agent | `agents` | `team_id`, `name`, `slug`, `system_prompt`, `model`, `capabilities` (json), `is_active` | The Claude-backed persona. Team-scoped as of 2026-08-10 (`HasTeamScope`, matching `ControlRoom`) — a deliberate revision of the earlier "ecosystem-wide, unscoped catalog" design, made when building the real creation UI forced the question of who can create one; `capabilities` is an open JSON bag, not yet schema-constrained |
| Agent Skill | `agent_skills` | `name`, `slug`, `icon` | Tag/category attached to agents many-to-many via `agent_agent_skill`. Stays global/unscoped deliberately — a shared tag vocabulary, not team data. No management UI exists yet (creating/editing skill tags) — only *assigning* existing ones to an agent, via the agent create/edit form |
| Conversation | `conversations` | `user_id`, `agent_id`, `title` | One thread between a user and an agent. Stays private per-user (`HasUserScope`) even though `Agent` became team-shared — your own chat history with a shared agent, not a shared team artifact |
| Message | `messages` | `conversation_id`, `role` (`user`/`assistant`), `content`, `tokens_used` | Ordered by `created_at`; full history is replayed to Claude on each turn (no truncation/summarisation yet) |
| Agent Usage Log | `agent_usage_logs` | `user_id`, `agent_id`, `tokens_input`, `tokens_output` | Written once per assistant turn — the basis for per-agent/per-user cost tracking |

Teams, users, and invitations come from the stock Jetstream scaffold and are shared-schema with the rest of the InfoDot ecosystem via the shared PostgreSQL instance.

## 3a. Domain Entities — Mining Dispatch (MVP scaffold, added 2026-08-01)

Added alongside the AI-agent domain above, not in place of it. Mirrors the entity list in Dot.Brain's `platforms/dot-central.md` §2, kept deliberately minimal:

| Entity | Table | Key fields | Notes |
|---|---|---|---|
| Control Room | `control_rooms` | `team_id`, `name`, `slug`, `mines_site_ref`, `is_active` | Tenant root, scoped to a Jetstream team (same tenancy mechanism as the rest of this app); `mines_site_ref` is a plain string pointer to a Dot.Mines site, not a live integration |
| Dispatch Decision | `dispatch_decisions` | `control_room_id`, `workflow_type` (enum), `sequence`, `decided_at`, `decided_by_user_id`, `summary` | The unit of record — identity is room + timestamp + sequence, enforced via a unique `(control_room_id, sequence)` index |
| Dispatch Workflow | — | — | Not a table. Modeled as the four-value `workflow_type` enum on `dispatch_decisions` (`assign`, `reroute`, `hold`, `stagger`) — a lookup concept, not an entity with its own lifecycle, per Dot.Brain §2 |
| Alert | `alerts` | `control_room_id`, `severity` (enum), `title`, `description`, `triggered_at`, `cleared_at` | Threshold/sentinel trips |
| Operator Session | `operator_sessions` | `control_room_id`, `user_id`, `shift_label`, `started_at`, `ended_at` | Control-room staffing context; deliberately carries no individual performance fields, per Dot.Brain §8's privacy note |
| Stale Session Proposal | `stale_session_proposals` | `operator_session_id`, `control_room_id`, `hours_silent`, `status` (`pending`/`ended`/`dismissed`), `resolved_at`, `resolved_by` | Added 2026-08-09. Opened by `central:scan-stale-sessions` (below) when an active session has logged no dispatch decision for 8+ hours; ending a session is never automatic — a human resolves the proposal |

Models: `App\Models\ControlRoom`, `DispatchDecision`, `Alert`, `OperatorSession`, `StaleSessionProposal`, all with `HasFactory` and relationships (`ControlRoom` has many of each child; `Team::controlRooms()` added). CRUD is via plain resource/nested controllers (`ControlRoomController`, `DispatchDecisionController`, `AlertController`, `OperatorSessionController`, `StaleSessionProposalController`) and Blade views under `resources/views/control-rooms/`, not Livewire — the only existing Livewire component (`AgentChat`) is chat-specific, so plain controllers matched the rest of the app's convention (dashboard, teams, profile are all controller/Blade) better than introducing Livewire for basic forms. Routes are registered in `routes/web.php` under the same `auth:sanctum` + Jetstream session group as the dashboard. A `MiningDispatchSeeder` and matching factories seed one demo control room with decisions across all four workflow types, two alerts, and an operator session.

**Stale-session alert scanning + approval gate (added 2026-08-09):** this platform's first scheduled background process (`routes/console.php`'s first `Schedule::` entry — previously zero background automation existed anywhere in this app). `php artisan central:scan-stale-sessions` runs hourly (`withoutOverlapping`, `onOneServer`) and, for every active (`ended_at` null) operator session: at 4+ hours since the session's last dispatch decision (or its start, if none), raises a deduplicated warning `Alert` and notifies the team via the existing in-app bell (`AlertRaisedNotification`, same path `AlertController::store()` uses for a human-raised alert); at 8+ hours, opens a `StaleSessionProposal` — but never ends the session itself. Resolving a proposal stays human-only, via a banner on the control room's show page wired to `StaleSessionProposalController::end()`/`dismiss()`, gated by the same `belongsToTeam()` check `OperatorSessionController::update()` already uses to end a shift manually. A real bug was found via TDD during this build, not assumed: this app runs Carbon 3.13.0, where `diffInHours()` returns a *signed* difference by default (Carbon 2 was always absolute) — an initial version returned `-5` for a session started 5 hours ago; fixed by passing `absolute: true` explicitly, which both major versions support.

Explicitly still out of scope (see §7): emitting any of this to an ecosystem event bus (`mining.dispatch.decided` etc. — the Alert/StaleSessionProposal rows above and the in-app notification are real, but nothing publishes outward), any Dot.Mines API call, and any Knowledge Pack publishing.

## 4. What's Not Built Yet

Named in the README as ecosystem-facing capability but absent from the current codebase — tracked here so the gap is explicit rather than implied. (Basic agent creation and chat itself used to belong on this list too, even though it was never written down here explicitly — it was silently assumed done. It's real now, as of 2026-08-10; see §1 and §7.)

- Knowledge-base upload / document grounding per agent (no `AgentKnowledge` model exists yet despite being listed as a domain model)
- Multi-agent routing/chaining for complex workflows
- Streaming responses (current implementation is a single blocking HTTP call)
- Per-agent public API endpoint for external platform integration (`routes/api.php` currently exposes only the stock `/user` Sanctum route)
- Any Knowledge Pack publishing/subscribing pipeline toward Dot.Brain

## 5. Events Emitted

No event bus integration exists in code today. The nearest analogues are database writes that a future publisher would translate into Knowledge Pack payloads:

| Would-be event | Current signal | Trigger |
|---|---|---|
| `central.agent.created` | `agents` row inserted | New agent configured |
| `central.conversation.turn_completed` | `messages` row pair (user + assistant) inserted | Each chat exchange |
| `central.usage.recorded` | `agent_usage_logs` row inserted | Each assistant turn, with token counts |
| `mining.alert.raised` | `alerts` row inserted (manually via `AlertController::store()`, or automatically via `central:scan-stale-sessions`, added 2026-08-09) | A sentinel trips, or an operator session goes 4+ hours with no dispatch decision |
| `mining.controlroom.session_flagged_stale` | `stale_session_proposals` row inserted (added 2026-08-09) | An operator session goes 8+ hours with no dispatch decision |

None of these are published anywhere yet — no queue job, webhook, or Brain-facing pack exists. `central:scan-stale-sessions` (§3a) is this platform's first background *process*, but it stops at writing local rows and an in-app notification; it is not itself an integration with anything outside this codebase. This section documents the shape the first real integration would take, not a shipped capability.

## 6. Connecting to Dot.Brain

Dot.Central is registered in Dot.Brain's platform map, and Dot.Brain's ingested view already describes a fuller integration package (Knowledge Pack manifest, domain metrics, a mining-dispatch decision loop with Dot.Mines, a tenancy model, and a worked publish→PR round-trip) at [`platforms/dot-central.md`](https://github.com/sakhilebhayi/Dot.Brain/blob/main/platforms/dot-central.md).

That document is written from Dot.Brain's ingestion perspective and, as of version 0.2.0 of this wiki, described a different product surface than what existed in this repository at the time: it frames Dot.Central as an *operational intelligence center for mining dispatch* (control rooms, dispatch decisions, fleet/haul-cycle events, alert precision) working tightly with Dot.Mines, while the code was an **AI agent command centre** only, with no mining/dispatch/control-room schema.

As of 2026-08-01 that gap is partially closed: this repository now also carries a mining-dispatch data model (§3a) — control rooms, dispatch decisions, alerts, operator sessions — as an MVP scaffold alongside the AI-agent domain. The remaining gap to Dot.Brain's fuller framing is real and tracked in §4/§7/Open Questions: no event emission, no Dot.Mines integration, and no Knowledge Pack pipeline exist yet for either domain. We are noting what's actually built rather than treating Dot.Brain's document as already implemented.

Until that reconciliation happens, this wiki takes precedence over `platforms/dot-central.md` for what Dot.Central *is*, per the ecosystem's ownership rule: platforms own their local knowledge, Dot.Brain ingests what's published.

We have not yet published a Knowledge Pack of any kind. Before we do, we need our own DKP manifest (`platform.dkp.json`), signing key, and an actual event-emission path (see §5) — none of which exist in code today.

See §3a for the full mechanism (`central:scan-stale-sessions`, `StaleSessionProposal`, human-only resolution). Ending a session automatically remains explicitly out of scope, by design, not as a deferred item.
- [x] **Real agent creation + chat UI (2026-08-10):** closed a gap that was never even written down as open, because it was silently assumed already done — the AI command centre's actual core loop (create an agent, open a conversation, chat) had no working path to it at all: no route to create an agent, no route to open a conversation, every dashboard action link was `href="#"`, and `AgentChat`'s own Blade view didn't exist (`ViewNotFoundException` waiting to happen). See §1 and §3 for what's real now: `Agent` became team-scoped (`HasTeamScope`), a plain `AgentController`/`ConversationController` pair handle CRUD and conversation creation/opening, and `AgentChat` was finished — real view, `mount(Agent, Conversation)` both required (no more ambiguous "guess the most recent conversation" fallback), loading/error states. Went through brainstorming → spec → plan first, since this is a real feature build, not a gap-fix (`docs/superpowers/specs/2026-08-10-agent-chat-ui-design.md`, `docs/superpowers/plans/2026-08-10-agent-chat-ui.md`). Two real, previously-latent bugs found live via this work's own tests, not by inspection: (1) the missing view, confirmed by an actual `ViewNotFoundException` the first time a test rendered the component; (2) `AgentChat`'s pre-existing `#[Computed] messages()` method silently collided with Livewire's own reserved `messages()` convention (custom validation messages) — the instant `#[Validate]` fired on a property update, Livewire called `messages()` expecting an array and got this component's chat-message `Collection` instead, crashing deep in Livewire's validation internals. Renamed to `conversationMessages()`. Neither bug had ever been exercised before, since nothing had ever actually rendered or interacted with this component. 18 new tests, full suite 88 (was 70), 81 passing, 7 skipped (pre-existing), 0 failed. Browser-based interactive login verification could not be completed in this environment: the preview launcher forces `SESSION_DRIVER=array` (visible directly in the process list), so sessions never persist across requests — a recurring characteristic of this specific preview mechanism, previously documented in the 0.7.0 changelog entry for the same reason. What *was* verified live: every new route correctly redirects an unauthenticated visitor to `/login`, proving the routing/middleware wiring; the authenticated flows themselves are proven by the real test suite, including the two bugs above that a browser click-through might easily have missed without the exact error text a test surfaces.
- [ ] Decide and document longer-term: does the dispatch domain stay a scaffold inside this repo, or is the agent hub meant to become the delivery mechanism for a deployed "dispatch agent" configuration instead of (or alongside) its own tables? The MVP scaffold answers "coexist for now"; the durable architecture question is still open.
- [ ] Wire dispatch-domain event emission out to an ecosystem event bus (`mining.dispatch.decided`, `mining.dispatch.outcome`, `mining.alert.raised/cleared`, `mining.controlroom.shift_summary`/`session_flagged_stale` per Dot.Brain §3 and §5 above) — the local Alert/StaleSessionProposal rows and in-app notification are real, but nothing publishes outward yet; explicitly deferred out of both the MVP pass and the stale-session gate
- [ ] Dot.Mines API/event integration for the operational lane (currently `mines_site_ref` is a bare string, no live connection)
- [ ] Build `AgentKnowledge` model and document-grounding pipeline
- [x] **Streaming responses (2026-08-10):** closed with a framing correction found before writing any code — the initial brief assumed Livewire had no native support for this and considered a dedicated SSE endpoint or Reverb/Echo broadcasting; neither was true. Livewire 3.6.4 (the version actually installed) has a native `Component::stream()` feature built for exactly this, and Reverb was confirmed directly to be an installed-but-entirely-unused dependency (see §2), not real infrastructure to build on. `AgentChatService::chat()` now sends `"stream": true` to Anthropic and parses its own SSE events as bytes arrive; `AgentChat::send()` passes a closure that calls `$this->stream()`, and the view gets one `wire:stream="reply"` target — no new routes. `chat()`'s return changed from `?string` to `array{text: ?string, complete: bool}`, since "full reply" and "partial reply before an interruption" are now distinguishable outcomes: a mid-stream failure keeps and persists whatever text was generated (real output, not discarded) alongside a distinct error message, rather than the prior all-or-nothing behavior. Full detail: `docs/superpowers/specs/2026-08-10-agent-chat-streaming-design.md`, `docs/superpowers/plans/2026-08-10-agent-chat-streaming.md`. 5 new tests (4 in a new `tests/Unit/Services/AgentChatServiceTest.php` — the first service-level unit test in this codebase — plus one more in `AgentChatTest`). Verification honestly scoped: no live Anthropic API key is configured in this environment, so the SSE parser is proven against `Http::fake()` responses built field-for-field to match Anthropic's real documented streaming format, not against a live call — not claiming more than that
- [ ] Ship a public per-agent API endpoint for cross-platform routing
- [ ] Define and publish the first Knowledge Pack (`platform.dkp.json`, signing key, `observation` payload) once there's a real event to report — covers both domains
- [ ] Multi-agent routing/chaining
